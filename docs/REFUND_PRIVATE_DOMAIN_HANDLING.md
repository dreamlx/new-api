# 退款私域人工处理方案

## 背景

当前系统已经具备 root 专用的充值退款执行接口，但前端暂不开放用户自助退款，也暂不开发“用户申请退款 -> 管理员审批 -> 自动原路退款”的完整线上流程。

现阶段更合适的产品策略是：系统内提供清晰的退款/售后引导，把用户引导到私域客服渠道（例如微信、企业微信）进行人工核验和处理。线上系统负责展示订单信息、降低沟通成本和保留必要线索；资金退款、额度追回、争议判断由人工完成。

## 目标

- 给用户提供明确的退款/售后入口，避免用户认为系统没有处理渠道。
- 不在普通用户侧暴露自动退款能力。
- 不让普通管理员误触发资金退款。
- 保留现有 root 手动退款接口作为应急处理能力。
- 通过私域人工客服覆盖复杂退款场景，例如额度已消耗、重复支付、支付异常、活动赠送、部分退款争议等。

## 用户侧设计

充值历史页可以增加“退款/售后”或“联系客服”入口，而不是直接命名为“退款”并触发自动流程。

入口建议：

- 按钮文案：`退款/售后`、`联系客服`、`人工处理`
- 展示位置：充值历史订单操作列
- 展示条件：已支付订单优先展示；未支付、失败、已过期订单可隐藏或展示为普通客服入口

点击后弹出人工处理说明弹窗，展示：

- 订单号
- 支付方式
- 支付金额
- 充值额度
- 支付/创建时间
- 客服微信号或企业微信入口
- 客服二维码

弹窗操作建议：

- 复制订单号
- 复制客服微信号
- 查看/保存客服二维码

用户侧文案建议：

> 如需退款或售后处理，请联系人工客服。请提供订单号、支付金额和账号信息。客服会核验订单状态、额度使用情况及支付渠道结果，符合条件后进行人工处理。

## 管理员侧设计

暂不建设完整审批流。后台重点支持人工核验：

- 充值历史支持搜索订单号。
- 展示用户、支付方式、支付金额、充值额度、订单状态、退款状态。
- 展示用户当前余额，便于判断是否可以追回额度。
- 可选增加“售后备注”或“客服备注”，用于记录人工处理结论。

当前 root 手动退款接口仍作为应急工具，不建议暴露给普通管理员页面。

## 退款处理原则

人工处理时建议遵循以下规则：

- 优先核验订单是否真实支付成功。
- 核验用户当前余额是否足够追回本次充值额度。
- 如果额度已消费，需人工判断是否拒绝、部分退款或要求用户补足条件。
- 活动赠送、订阅套餐、优惠订单等特殊订单需单独判断。
- 支付宝退款通常可同步确认结果。
- 微信退款为异步结果，需等待退款回调或支付商户平台状态确认。

## 技术边界

本方案暂不新增以下能力：

- 用户退款申请表
- 管理员退款审批流
- 用户自助原路退款
- 普通管理员执行退款
- 自动部分退款计算

当前已有后端退款能力作为执行层保留：

- `POST /api/topup/refund/prepare`
- `POST /api/topup/refund`
- `POST /api/user/wxpay/refund/notify`

这些接口仍应保持 root 专用，不作为用户侧产品能力开放。

## 最小落地方案

第一阶段只做轻量引导：

1. 后台系统设置增加客服微信号、客服二维码配置。
2. 用户充值历史页增加“退款/售后”入口。
3. 弹窗展示订单信息和客服联系方式。
4. 支持复制订单号和客服微信号。
5. 不改变现有退款接口、订单状态机和资金处理逻辑。

后续如果退款量增长或人工处理成本过高，再考虑建设正式的退款申请和审批流程。
