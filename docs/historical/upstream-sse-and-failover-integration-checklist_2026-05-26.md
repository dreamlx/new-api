

## 💡 第一部分：需要向对方确认的核心问题（确认合格服务）

这部分问题旨在试探对方的底层架构是否足够健壮，能否承受住 Agent 工具（如 Codex/Claude Code）的严苛压榨。

### 1. 流式传输（SSE）与协议完整性问题

* **核心发问**：*“你们的 `exchangetoken` 在进行上游协议转换（如 Anthropic/OpenAI 互转）时，是否完整保留了所有的流式元数据（Metadata，如 `content_block_delta` 或 Tool Call 字段）？是否存在中间件级缓存（Buffering）？”*
* **业务痛点**：今天测出的“HTTP 200但立刻空Body关流”，很可能是上游在协议转换时遇到某些不认识的字段直接抛了异常，或者其 Nginx 没关缓冲。必须确认他们是否支持**零缓冲的标准 SSE 穿透**。

### 2. 长连接与超时断开机制（Timeout & Keep-Alive）

* **核心发问**：*“在处理 Agent 深度思考（如推理模型或长文本生成、多步骤 Tool Call）时，你们的网关和 Exchange 服务允许的最大 `read_timeout`（读超时）和 `keepalive` 时间是多少？”*
* **业务痛点**：Agent 思考可能需要十几秒甚至几十秒才吐第一个 Token，如果上游网关默认 10 秒没数据就掐断连接，转卖出去的 API 就会大面积卡死。

### 3. 并发限制（TPM/RPM）与级联重试策略

* **核心发问**：*“`exchangetoken` 在应对高并发高负载时，限流（Rate Limit）是返回标准的 HTTP 429 还是其他自定义状态码？当上游出现分布式波动时，你们内部有无自动重试机制？如果有，流式请求的重试会不会导致连接中断或返回重复的 Chunk？”*
* **业务痛点**：我们做转卖，下游的并发是不可控的。如果上游限流返回的格式不标准，我们的 New-API 就无法精准识别并切换渠道，会直接把 500 错误抛给终端客户。

## 🛠️ 第二部分：准备与对接规范

### 1. 提供标准的 SSE 联调沙盒与端到端测试用例

* **要求**：要求对方提供一个**绝对不经过任何 Nginx 缓冲、纯净的 `/v1/messages` 或 `/v1/chat/completions` 流式测试 Endpoint**。
* **目的**：方便我们的研发直接用 `curl -N` 排查到底是 LH platform 内部转发坏了，还是他们 Exchange 出来的 Token 流本来就是断的。

### 2. 给出明确的错误码对照表（Error Mapping）

* **要求**：输出一份 `exchangetoken` 的错误码白皮书。例如：
* Token 额度耗尽返回什么？
* 上游并发超限（429）时，Exchange 层是直接透传 429 还是包成 500？


* **目的**：我们的 New-API 需要根据这些状态码做精细化的失败重试（Failover）和渠道自动切换。

### 3. 明确白名单与网络拓扑配置

* **要求**：双方明确对接节点的 IP 白名单。如果涉及跨境或多云路由（如涉及海外节点中转），需要他们提供最优的接入 BGP 节点或 Anycast IP。
* **目的**：降低网络抖动引发的流式断流。
